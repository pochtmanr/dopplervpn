## Stage 0 — before anything

Confirm nothing has drifted since the table above. `apply-node-baseline.sh` asserts the
expected config shape and aborts if a node deviates; a node that aborts was changed by
hand and needs a human look, not a retry.

## Stage 1 — stats agent v2

Lowest risk in the whole rollout. The agent is a monitoring sidecar; restarting it drops
no user traffic and touches no xray config.

Deploy to one node first. Japan is the quietest at 24 sockets.

```
cd landing/infrastructure/monitoring
./deploy-stats-agent.sh 20.46.122.212
```

Confirm the response time collapses from ~2.4s to well under 100ms, and that the payload
now carries `agent_version: 2`. Then walk the remaining nodes. Russia will fail; that is
expected and the script reports it without aborting the run.

**Two things will look like breakage and are not.** Redeploys used to be silent no-ops
because `enable --now` does nothing to a running unit, so this is the first deploy in a
while that actually replaces the running agent. And once v2 reports honestly, seven nodes
start saying their exit is blocked by OpenAI. That has been true for months. Nothing the
deploy did caused it.

Ship the admin panel and the n8n workflow changes before or alongside this, so the honest
reachability reporting lands somewhere that treats it as a standing condition rather than
an incident.

## Stage 2 — node baseline, stage one

Additive only: the `api` inbound, `stats`, `policy`, the `block` outbound, and the four
routing rules. This is what fixes the latency at the source and unlocks per-user
accounting.

Run `verify-egress-exposure.sh` first and read the result. It reports the link-local
metadata endpoint, node loopback, and Poland's `127.0.0.1:8000` Marzban API separately,
because the severity genuinely differs between them.

Then `apply-node-baseline.sh`, one host per run, in this order: Japan, UAE, Poland 2,
Canada, Sweden, United States, Hong Kong. Quietest first, busiest last. Verify each with
`verify-node-baseline.sh` before starting the next.

**Poland is not in that list.** It runs xray 24.12.31 against the fleet's 26.3.27, and
Marzban regenerates its config from panel state, so a hand-edit is at risk of being
overwritten in a way the bare-xray nodes are not. Its branch gates on running `xray -test`
inside the container. Do it last, deliberately, and read the applier's version check.

## Stage 3 — node baseline, stage two, DNS

Separate stage because it is the only part that changes the behaviour of traffic that
works today. A `dns` block alone is inert under freedom's `AsIs`, so making it real means
patching the `direct` outbound's `domainStrategy`, which changes how every destination for
every user is resolved.

The motivation is real: the hosting provider currently sees every domain every user
resolves, which sits badly beside a zero-logs claim. But this is the stage most likely to
produce a user-visible regression, and it is the first thing to roll back if a streaming
or CDN complaint follows a rollout.

Apply it only to nodes where stage one is verified. One node, then wait a day.

## Stage 4 — metrics history

Apply the `server_metrics` migration, then deploy the collector:

```
cd landing/infrastructure/monitoring
./deploy-metrics-collector.sh
```

It runs on Poland only, and the deploy script makes you retype the hostname to target
anything else, because it ships the Supabase service-role key and a VPN exit node is the
machine most likely to be seized or reimaged. A systemd timer sweeps the fleet every 60
seconds and a second timer runs retention daily at 03:20 UTC, chosen over pg_cron because
that extension's availability is unconfirmed.

Let it accumulate before expecting the charts to say anything. The admin panel degrades to
"no history yet" until there is data, which is correct on day one rather than a bug.

**One artefact to expect in the history.** The collector faithfully records a blocked exit
for all seven Azure nodes from the moment agent v2 lands. That will appear in the series as
a step change on deploy day even though nothing changed, because it is the day we started
measuring. Anyone reading that chart later needs to know it is the instrument appearing,
not the fleet degrading.

## Stage 5 — per-identity VLESS credentials

The largest change and the one that finally makes a real user count possible. It depends
on stage 2 being verified everywhere, because the reconciliation works through the xray
HandlerService API rather than by restarting.

Reconcile the live `get_servers_v2` definition with `pg_get_functiondef` before applying
anything. The repo is not authoritative: the live function carries a `min_tun_version`
gate that exists in no migration file, and replaying an old snapshot would silently revert
it along with the `tunnel_mode` and `client_flags` keys.

Keep the shared UUID authorised throughout, so devices holding a cached config keep
working. Retire it as a separate, later decision once the panel shows per-account users
actually connecting.

**Retiring the shared UUID is the one step that cannot be done live.** xray's user API
removes a client by its `email` field, and the fleet's shared client entry has none, so it
is invisible to the API: an add reports "Added 0" with no error at all. Every per-account
user can be added and revoked with no restart and no dropped sessions, but removing the
legacy shared entry needs an xray restart on each node. Plan it as a scheduled reconnect,
one node at a time, not as a routine sync.

Two related facts worth knowing before you run any of this. The subcommands are `adu` and
`rmu`, not `adduser` and `rmuser`, and **both exit 0 even when they fail** — a duplicate
add, an unknown email and a nonexistent inbound tag all print an RPC error and return
success. The only trustworthy signal is the `Added N user(s) in total.` trailer. The sync
service parses it; anything else you script against that API must too.

## Stage 6 — exit proxies

Inert until credentials exist, and deliberately so. With zero proxies attached, a node's
rendered config is identical to the one without the feature, and that identity is the
acceptance test.

Before buying anything: two or three endpoints for the **entire fleet**, not per node.
Only the flagged domain set crosses the upstream. Pool size follows concurrent ChatGPT
users, not node count. Put them in countries OpenAI actually serves; it does not serve
Hong Kong or Russia, so matching those nodes' locations would keep ChatGPT broken.

Two things to settle before switching it on with real credentials. Traffic through a
third-party proxy is visible to that provider at the SNI and destination level, which the
privacy policy does not currently cover. And the landing page already claims Doppler
rotates IP addresses, which will be true only for the flagged domain set even after this
ships.
